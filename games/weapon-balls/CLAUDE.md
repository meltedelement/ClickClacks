# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this folder, the game module of the repo (the repo root's CLAUDE.md covers how the modules fit together). Paths here are relative to `games/weapon-balls/`.

Weapon Balls: balls with spinning weapons bounce around an arena and fight. Vanilla JS (ES modules) + Canvas 2D, bundled with Vite. No framework, no runtime dependencies. README.md covers the file layout and the step-by-step for adding weapons/abilities; read it before adding content.

## Commands

```sh
npm run dev                              # Vite dev server with hot reload
node tools/headless-display.js           # a display page without a browser: plays queued matches with the real sim
npm run build                            # production build to dist/
npm run balance                          # headless balance run, 500 matches per pairing
npm run balance -- -g 2000 -w sword,mace # subset of weapons, more matches
npm run balance -- -s 42 --json a.json   # fixed seed; rerun after a tweak and compare
npm run balance -- -w sword,sword+lifesteal,mace  # fighters are weapon[+upgrade[:stacks]...] specs
npm run balance -- --help
npm run sweep                            # upgrade sweep: outlier upgrades/transformations/stacks per weapon (-n for plan size)
npm run flawless                         # find a seeded match won without taking a hit (--queue plays it on ?display); GUI at /flawless.html
```

The game has no tests or linter. The balance script is the main way to verify gameplay changes: run it with a fixed seed before and after a tuning change. Win rates outside 45–55% (weapon) or 40–60% (single matchup) are flagged.

## Architecture

**`src/sim/` is pure and headless.** It must not touch the DOM, `window`, or audio. `tools/balance.js` imports `Simulation` and the weapon registry directly and runs it in Node worker threads. Anything browser-only goes in `src/game/` or `src/ui/`. Weapon and ability `draw*` methods only receive a `ctx` and are never called by the sim, so they're fine.

**Randomness must go through `Math.random`.** The balance tool makes matches reproducible by replacing `Math.random` with a seeded PRNG (mulberry32) per match. Don't introduce another RNG source inside sim/weapons/abilities.

**Fixed timestep.** `Game` steps the sim at `CONFIG.physicsHz` (120 Hz) with an accumulator; the balance tool steps with the same `dt`. Hitstop, screen shake, particles and sound live only in `Game`/`Effects`/`Sound`, never in the sim, so they don't affect outcomes.

**Sim → presentation is one-way, via events.** `Simulation` calls `onEvent(type, data)` for `hit`, `dodge`, `damage` (non-weapon damage from `sim.dealDamage`), `parry`, `block`, `death`, `end`, `ability`, `upgrade` and `grow` (royale only) (the event list is documented at the top of `Simulation.js`). Two consumers exist and both may need updating when an event changes: `Game.handleSimEvent` (effects + sound) and the `onEvent` in `tools/balance.js` (stats).

**Combat resolution order each step** (`Simulation.resolveCombat`): weapon-vs-weapon clashes → weapons touching a shield → spiked shields (and off-hand swords) touching balls → weapon-vs-ball hits. Only `weapon.heldShields` take part (a thrown shield has `away` set). In `applyHit` the target's dodge is rolled first, then the target's upgrades may cancel the hit (`preventHit`), then the attacker's crit (`rollCrit(point)`: an upgrade's `critsAt(point)` can force one), then the attacker's damage (`getDamage(point)`, including upgrades' `damageMultiplierAt(point)`), then the target's armor, `damageTakenMultiplier` and status multipliers. Dodge and crit only call `Math.random` when their chance is above 0, so plain matches reproduce exactly. A ball killed earlier in the step still swings, so same-step trades are draws regardless of slot order. Any weapon touching another weapon or a shield is blocked for that step and cannot hit. A parry only fires if both weapons pass `canParry`; a shield block only needs the attacker's. A weapon whose `clashesWith(other)` is false swings through that weapon unblocked while the other stays blocked (Daggers against other Daggers while they can't parry, which prevents dagger-vs-dagger stalemates). `unblockable` weapons skip both checks, and a ball with a `guardBroken` status (Tackler) neither clashes with other weapons nor blocks with its shields. Per-target hit cooldowns are keyed by weapon (`Ball.hitCooldowns`), which is why multi-hit abilities call `target.clearHitCooldown(weapon)`.

**Weapons** (`src/weapons/`) are one or more straight blade segments spinning around the ball; hitboxes are capsules (`thickness` is half-width). Stats (`damage`, `spinSpeed`, `length`, ...) are per-instance and mutated in `onHit`/`onParry` for scaling. A weapon may also carry shields in `this.shields` (see `Sword.js`); `OffhandSword` is a `Shield` subclass, so shield upgrades work on it too. Register new weapons in `src/weapons/index.js`; the UI and balance tool pick them up from `WEAPONS`. Every collision test in `collisions.js` (and `Drone.touch`) first rejects pairs whose centres are too far apart, using `Weapon.bladeReach`/`guardReach` and `Shield.reach`: upper bounds on how far the hitboxes extend from the ball's centre. A weapon that overrides `getSegments` or a shield that overrides `getSegment` must override the matching reach getter too (Drone, OffhandSword), or it will silently miss hits. Per-step sim code is the balance tool's hot path, so keep it allocation-light: no `Array.from`/`map` callbacks in geometry, and `Simulation.aliveBalls` and `Weapon.heldShields` return shared arrays that callers must not modify.

**Abilities** (`src/abilities/`) modify behaviour only through getters (`spinMultiplier`, `bonusDamage`, `damageMultiplier`, `knockbackMultiplier`, `damageTakenMultiplier`, `controlsMovement`, `unblockable`, `unstoppable`, `disarmed`, `bladeSpread`). `Weapon` combines these across the ability and all upgrades (`Weapon.multiplier` / `Weapon.sum` / `Weapon.anyModifier`; flat "+N damage" bonuses go in `bonusDamage`, never as a `1 + N / damage` multiplier, or two of them multiply each other) and proxies the result to the engine. A new kind of modifier means adding the getter to both `Ability` and `Upgrade`, a proxy on `Weapon`, and reading it wherever the engine needs it (`Ball`, `collisions.js`, `Simulation`). Multi-phase abilities track `this.phase` and must call `this.end(sim)` themselves to start the cooldown. `ChargeDash.js` is the fullest example. Ability gameplay numbers are instance fields set in the constructor, not module constants, so upgrades can change them.

**Upgrades** (`src/upgrades/`) are the roguelike layer's input to the sim. `Simulation` takes one plain-data loadout per fighter (`{ weapon: 'sword', upgrades: ['lifesteal'] }`), resolved through the `WEAPONS` and `UPGRADES` registries. `Ball` builds the weapon, then applies each upgrade (`apply()`), then sets `hp = maxHp` and the starting velocity. Upgrades stack: a repeated id becomes one instance with `stacks` counted up, and `apply()` runs once per copy, so getters and hooks must scale with `this.stacks` themselves. Upgrades with `static transformation = true` (`sword-transformations.js`, `spear-transformations.js`, `mace-transformations.js`, `daggers-transformations.js`) are applied before all others, whatever the loadout order, and within each group a lower `static order` goes first (Dual Wielder before Stalwart, Slippery before Rogue, Crusher after Rubber Mace). That order is also the order every hook runs in. An upgrade can stop an ability of its weapon from starting with `allowsAbilityStart` (Dancer). Timed effects on a ball (burn, net) are `Status` subclasses (`src/sim/Status.js`) added with `ball.addStatus`; `Ball` ticks them and folds their `speedMultiplier`/`damageTakenMultiplier`/`damageDealtMultiplier` in (`Simulation` scales a ball's weapon hits and its `dealDamage` by the last); `guardBroken` is read by `Simulation`, and `Ball.registerWallBounce` passes wall bounces to both upgrades and statuses. Balls touching (from `resolveBallCollision`) reach upgrades as `onBump(otherBall, sim)` every step they touch. Stat boosts stack linearly from the starting value (`this.base ??= ...`). `resolveUpgrades` rejects unknown ids, weapons not in `static weapons`, more than `static maxStacks`, and missing `static requires`. Shared upgrades live in `common.js`, weapon-only ones in `<weapon>.js`, all registered in order in `index.js` (that order is the menu order). They affect outcomes, so they follow the sim rules (headless, `Math.random` only). Their `draw*` methods are called only by `Renderer` and `Weapon.draw`. Run state, choosing upgrades and so on belong outside `src/sim`/`src/upgrades` and only produce loadouts; the menu's per-fighter upgrade picker (`Controls`) is the current one.

**Royale** (`new Simulation(loadouts, { royale: true })`, `CONFIG.royale`) is a crowd in an arena sized to it (`sim.arena`, so never read `CONFIG.arena` for the live arena; drawing code without a sim uses `ball.arena`). `knockOut(ball, killer)` hands the victim's mass to the killer (`Ball.grow`): `ball.size` rises, and the radius, blade `length`/`gap`/`thickness` and shield geometry are multiplied up in place (`Weapon.scaleGeometry`), so all hit code just sees bigger numbers. Any other px value an upgrade holds on to across time (a temporary `length += added`) must scale in `onGrow(factor)`. Trigger ranges ("only when an enemy is within N px") go through `enemyWithin` (`src/sim/targeting.js`), which scales them with the owner's size and adds both balls' grown radii, using nominal radii so Compact doesn't shorten them; never compare a raw `distance` to a fixed range. Drawing happens at size 1 under a scaled canvas (`Weapon.draw`, `Weapon.drawBladeAt` for blades drawn away from the ball, `Ball.atUnitSize`), so `drawLocal` keeps its proportions; a new weapon with its own `draw` needs the same. With hundreds of balls the pair loops go through `src/sim/broadphase.js` (neighbour lists, still in slot order); a normal match gets every pair, so its results are unchanged. Every `size`/`mass` is 1 outside a royale: keep royale code from changing normal matches (check with a seeded balance run before and after). `Game.handleRoyaleEvent` gives royales lighter effects (no hitstop, shake or damage numbers).

**Sound is keyed by string ids.** `Sound.ability(phase)` switches on the phase name passed to `Ability.emit` (`swipe`, `charge`, `dash`, `throw`, `catch`, `slam`), and `Sound.hit` checks weapon `id` against a `BLUNT` set. New abilities or weapons with their own sound need a matching case in `src/game/Sound.js`.

**Effects quality is adaptive and lives outside the sim.** `src/game/Quality.js` is a page-wide controller: every `Game` reports its animation-frame timestamps, and when the frame interval runs past the display's refresh period it steps the particle budget and the canvas backing-store resolution down (`Effects.setProfile`, `Renderer.setResolutionScale`), restoring them once frames are comfortable. `?quality=high|medium|low|minimal` pins a level instead. Keep all of this presentation-only: it must never reach `src/sim` or change match outcomes. `Effects` pools its particle/text objects and blits a cached spark sprite, so its `draw` allocates nothing and makes one canvas call per spark — a fight can have thousands live, especially with several arenas on the display page. On the display page only on-grid screens run: `TournamentDisplay` starts and stops each `Game` (`Game.start`/`stop`), so an idle screen neither simulates nor draws. HP numbers, name labels and floating damage numbers go through `src/game/TextSprites.js` (rendered once into a cached canvas, then blitted), because `fillText`/`strokeText` every frame are slow; draw new per-frame text the same way. `tools/bench-render.js` measures this path headlessly (canvas calls, particle counts, frame ms) — run it before and after a change to effects or drawing.

**Match API** (`server/`, documented in README.md). Plain Node, no dependencies. It is the game's implementation of the Match Host contract (`contracts/match-host.d.ts` at the repo root), the only thing the tournament service knows of the game: keep its field names (`characters`, `decisive`, `settings`, `displayPath`, `result.scores`, `POST /validate` with `settings`) when changing it. The contract's "characters" are this game's fighters: the API says `characters`, the game's own code keeps saying fighters. `server/matches.js` is one request handler, used by `server/index.js` (`npm start`, serves `dist/`) and by the Vite plugin in `vite.config.js` (`npm run dev`). An external program queues matches (two fighters or more) over HTTP, optionally tagged with a `ref`, and can check loadouts with `POST /api/validate` instead of copying the rules. The server puts up to `SCREENS` (default 4) matches on screens at once; the page opened with `?display` (`src/ui/TournamentDisplay.js`) runs one `Game` per screen in a grid, plays them and POSTs each result back (with `sim.ranking`); the display's result is the official one. `api/game.d.ts` is the contract for callers (its types extend the Match Host ones): change it together with `matches.js`. `Game` takes matches from `chooseMatch()` as `{ fighters, seed?, timeLimit?, tiebreak? }`; with `tiebreak: 'hp'` the sim (`endOnTime`, `checkForWinner`) never ends in a draw. `Controls` takes a list of games and applies settings to all; on the main page that list is `Arenas.games` (`src/ui/Arenas.js`), which the menu's Arenas setting grows and shrinks, and `Controls.setAll` remembers settings so added arenas get them. `Sound` shares one audio context per page: `Sound.muted` is the page-wide mute, and each instance has its own `muted` (a display screen's mute button). For a seeded match it swaps in `mulberry32` (`src/sim/random.js`) as `Math.random` only while the sim is being built or stepped. It restores the real one inside sim event handlers, so effects and sound never use up the seeded sequence. Keep that when changing `Game`. Fighters can have a `name` (team), shown above the ball and in the winner banner, and a `color` (`#rrggbb`) that replaces the weapon's ball colour.

**Tuning lives in two places:** shared numbers (arena, ball speed/HP, knockback, cooldowns, hitstop) in `src/config.js`; weapon- and ability-specific numbers as constants or constructor stats in each weapon/ability file.
